## Architecture

the dashboard is a [TanStack Start](https://tanstack.com/start) app (Bun / Nitro server) that:

- talks to Jaeger's HTTP query API **server-side** — Jaeger does not need CORS headers, and the browser never calls Jaeger directly.
- maintains its own **issue store** (SQLite or Postgres via Drizzle) for aggregated error history that survives Jaeger's retention window.
- runs a **background ingester** fiber that polls Jaeger on a configurable interval and copies error spans into the issue store.

in 0.1.0, the app is **read-only** over Jaeger — it does not write traces, does not manage users or organizations, and does not send alerts.

## Docker Compose example

the repository ships a `docker-compose.yaml` that starts Jaeger alone (useful for local dev). for production you'll want to run Jaeger and the dashboard together:

:::info
the compose file and Dockerfile below are illustrative starting points. they are not tested in CI. adapt them to your infrastructure (secrets management, volume paths, network names, etc.) before deploying.
:::

```yaml title="docker-compose.yaml"
services:
  jaeger:
    image: jaegertracing/jaeger:latest
    ports:
      - "16686:16686"   # query API
      - "4318:4318"     # OTLP HTTP
      - "4317:4317"     # OTLP gRPC
    volumes:
      - ./jaeger-config.yaml:/etc/jaeger/config.yaml:ro
    command: ["--config", "/etc/jaeger/config.yaml"]
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:16686/"]
      interval: 5s
      timeout: 3s
      retries: 5

  traces:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      JAEGER_URL: http://jaeger:16686
      TRACES_DB: /data/traces.db
    volumes:
      - traces-data:/data
    depends_on:
      jaeger:
        condition: service_healthy

volumes:
  traces-data:
```

## Dockerfile starting point

```dockerfile title="Dockerfile"
FROM node:22 AS base
COPY --from=oven/bun:1 /usr/local/bin/bun /usr/local/bin/bun
RUN corepack enable
WORKDIR /app

# install dependencies
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml turbo.jsonc ./
COPY apps/web/package.json ./apps/web/
COPY apps/docs/package.json ./apps/docs/
COPY packages/core/package.json ./packages/core/
COPY packages/react/package.json ./packages/react/
RUN pnpm install --frozen-lockfile

# copy source
COPY . .

# build apps/web
RUN cd apps/web && pnpm run build

EXPOSE 3000
CMD ["bun", "run", "./apps/web/server/index.ts"]
```

the `start` script in `apps/web/package.json` is `pnpm run build && bun run ./server/index.ts`. the Dockerfile above separates the build step so the final image layer is only the compiled output and the runtime server.

## Storage: SQLite vs. Postgres

the issue store driver is selected automatically at startup based on whether `DATABASE_URL` is set. migrations run automatically for both drivers — there is no manual migrate step.

| | SQLite | Postgres |
|-|--------|---------|
| how to enable | absent `DATABASE_URL` (default) | set `DATABASE_URL` |
| config | `TRACES_DB=./traces.db` (path to file) | `DATABASE_URL=postgresql://user:pass@host/db` |
| best for | single-instance, zero-config, dev, small deployments | durability, multi-instance, shared access |
| persistence | file on disk — mount a volume | external Postgres instance |

:::info
the issue store holds only the aggregated error data — fingerprints, occurrence counts, and pointers back to Jaeger trace/span IDs. pointing at a different database does not affect Jaeger traces; you only lose local issue history.
:::

## Resource expectations

the pitch is small footprint:

- **Jaeger in-memory** idles around 200 MB.
- **the dashboard** is a lightweight Bun/Nitro server. memory usage scales with ingester concurrency and issue store size, but stays well under 200 MB for typical small-to-medium deployments.
- compare: Sentry self-hosted or SigNoz require ~2 GB+ of auxiliary services (Redis, Kafka, Clickhouse, etc.).

:::warning
the in-memory Jaeger backend is for local dev and demos. it caps at 10 000 traces and loses all trace data on restart. for real retention, point Jaeger at a durable storage backend (Elasticsearch or Cassandra) by updating `jaeger-config.yaml`. the dashboard works the same regardless of the Jaeger backend — only the trace retention window changes.
:::

## Environment variables

see [configuration](/docs/app/configuration) for the full list. the minimum set for a production deployment:

```bash
JAEGER_URL=http://jaeger:16686

# SQLite (single instance, simplest)
TRACES_DB=/data/traces.db

# OR Postgres (durable, multi-instance)
# DATABASE_URL=postgresql://user:pass@postgres:5432/traces
```
