## Architecture

traces is two processes in front of Jaeger:

- the **engine** (`services/engine`) is a headless Bun server. it talks to Jaeger's HTTP query API, owns the **issue store** (SQLite or Postgres) that keeps aggregated error history past Jaeger's retention window, and runs the **background ingester** that polls Jaeger and copies error spans into that store. it serves a typed [oRPC](https://orpc.dev) API at `/rpc/*` and a `/health` check.
- the **web app** (`apps/web`) is a [TanStack Start](https://tanstack.com/start) server (Bun / Nitro) that renders the dashboard. it has no data of its own: server-rendered pages call the engine directly, and the browser's API calls go to the web server's `/api/rpc/*`, which forwards them to the engine.

```
browser → web (:3000) → engine (:4000) → Jaeger (:16686)
                              └→ SQLite file or Postgres
```

Jaeger needs no CORS headers and the engine needs no public address: only the web app has to be reachable by users, and only the engine has to reach Jaeger and the database. [configuration](/docs/app/configuration) lists which environment variable belongs to which process.

the app is **read-only** over Jaeger — it does not write traces, does not manage users or organizations, and does not send alerts.

:::warning
the engine has no authentication. anyone who can reach it can read all data and resolve issues. keep it on a private network and expose only the web app.
:::

## Running it

traces runs from a checkout of the repository; Docker images are not provided yet. you need [Bun](https://bun.sh) and [pnpm](https://pnpm.io), plus a Jaeger v2 instance (the repository's `docker-compose.yaml` starts one for local use).

```bash
pnpm install --frozen-lockfile
```

start the engine:

```bash
JAEGER_URL=http://jaeger:16686 \
TRACES_DB=/var/lib/traces/traces.db \
PORT=4000 \
bun services/engine/src/main.ts
```

check it:

```bash
curl http://localhost:4000/health   # {"status":"ok"}
```

build and start the web app, pointing it at the engine:

```bash
cd apps/web
pnpm run build
ENGINE_URL=http://localhost:4000 PORT=3000 bun .output/server/index.mjs
```

### Running the engine without the web app

the engine works on its own. start it as above and any oRPC client can use it; for example, listing the services Jaeger knows about:

```bash
curl -X POST http://localhost:4000/rpc/traces/listServices \
  -H 'content-type: application/json' -d '{"json":{}}'
# {"json":["api","payments","web"]}
```

the ingester starts with the engine, so issues accumulate even when no dashboard is running. the procedure types are in the workspace package `@traces/contract` (not published to npm). procedures use POST, and clients should branch on the error `code` in a failed response rather than on the HTTP status.

## Storage: SQLite vs. Postgres

the engine selects the issue store driver at startup based on whether `DATABASE_URL` is set. migrations run automatically for both drivers — there is no manual migrate step. these variables belong to the engine; the web app never touches the database.

| | SQLite | Postgres |
|-|--------|---------|
| how to enable | absent `DATABASE_URL` (default) | set `DATABASE_URL` |
| config | `TRACES_DB=./traces.db` (path to file) | `DATABASE_URL=postgresql://user:pass@host/db` |
| best for | single-instance, zero-config, dev, small deployments | durability, multi-instance, shared access |
| persistence | file on disk — put it on a persistent volume | external Postgres instance |

:::info
the issue store holds only the aggregated error data — fingerprints, occurrence counts, and pointers back to Jaeger trace/span IDs. pointing at a different database does not affect Jaeger traces; you only lose local issue history.
:::

## Resource expectations

the pitch is small footprint:

- **Jaeger in-memory** idles around 200 MB.
- **the engine and the web app** are two lightweight Bun processes. memory usage scales with ingester concurrency and issue store size.
- compare: Sentry self-hosted or SigNoz require ~2 GB+ of auxiliary services (Redis, Kafka, Clickhouse, etc.).

:::warning
the in-memory Jaeger backend is for local dev and demos. it caps at 10 000 traces and loses all trace data on restart. for real retention, point Jaeger at a durable storage backend (Elasticsearch or Cassandra) by updating `jaeger-config.yaml`. the dashboard works the same regardless of the Jaeger backend — only the trace retention window changes.
:::

## Environment variables

see [configuration](/docs/app/configuration) for the full list. the minimum set for a production deployment:

```bash
# engine
JAEGER_URL=http://jaeger:16686

# SQLite (single instance, simplest)
TRACES_DB=/var/lib/traces/traces.db

# OR Postgres (durable)
# DATABASE_URL=postgresql://user:pass@postgres:5432/traces

# web app
ENGINE_URL=http://localhost:4000
```
