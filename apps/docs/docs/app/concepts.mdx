## Traces and spans

a **trace** is a directed acyclic graph of **spans** representing a single request as it propagates through your services. the app follows the [OpenTelemetry data model](https://opentelemetry.io/docs/concepts/signals/traces/).

each span records:

- service name and operation name
- start time, end time, and duration
- status (`ok` / `error` / `unset`)
- attributes — key-value pairs from instrumentation
- events — point-in-time annotations, including `exception` events that carry type, message, and stacktrace

a span is treated as an **error span** when `status.code === 'error'`.

## Jaeger backend

the engine talks to Jaeger v2's HTTP query API (`/api/v3/…`). the `TraceBackend` interface in `@traces/core` abstracts the transport, so the same components work whether data comes from Jaeger, a test fixture, or a future backend.

only the engine talks to Jaeger — Jaeger does not need to be reachable from the browser or the web app, and no CORS configuration is required on the Jaeger side.

## Issues

an **issue** is a group of error occurrences that share the same fingerprint. issues are not surfaced by Jaeger — they are computed from spans by the background ingester and stored in the local issue database (SQLite or Postgres).

### fingerprinting

two code paths produce a fingerprint, depending on whether the span has `exception` events attached:

**span with exception events** — fingerprint is a SHA-256 hash of:

```
[serviceName, exception.type, normalizedMessage, topInAppStackFrame?]
```

`topInAppStackFrame` is the first stack frame whose file path does not contain `node_modules` or `node:internal`. if no in-app frame is found, the field is omitted.

**error span with no exception events** — fingerprint is a SHA-256 hash of:

```
[serviceName, spanName, normalizedStatusMessage?]
```

### message normalization

before hashing, the exception message (or status message) is normalized to collapse variable tokens that would otherwise create a separate issue per unique ID:

| Pattern | Replacement |
|---------|-------------|
| UUID (`xxxxxxxx-xxxx-…`) | `<UUID>` |
| Hex literal (`0x…`) | `<HEX>` |
| Long hex string (16+ chars) | `<HEX>` |
| Quoted string (`'…'` or `"…"`) | `<STR>` |
| Number | `<NUM>` |

two errors that differ only by a user ID, request ID, or port number will group into the same issue.

### issue status and regressions

issues have exactly two statuses: **unresolved** and **resolved**.

- **resolve** — stamps `resolvedAt = now`; the issue moves out of the active list.
- **unresolve** — clears `status` back to `unresolved` and clears `resolvedAt`.
- **auto-reopen** — if a resolved issue receives a new matching occurrence, it automatically flips back to `unresolved`. `resolvedAt` is preserved, keeping the date of the last manual resolve.
- **regression** — an issue is flagged as regressed when it is unresolved, has a non-null `resolvedAt`, and `lastSeen > resolvedAt`. this means it was previously resolved and a new occurrence reopened it. the UI surfaces this state with a regression badge.

### occurrence retention

the `occurrenceCount` field is a lifetime total — it is incremented on every real occurrence and never decremented. however, the stored occurrence rows are capped at the latest **1 000** per issue to bound database size. the count stays accurate even after old rows are pruned.

## Ingester polling and cursors

the background ingester runs on a fixed interval (default 30 s) and continuously copies error data from Jaeger into the local issue store.

### poll cycle

each tick:

1. lists all services known to Jaeger.
2. for each service, fetches traces in a computed time window.
3. for each returned trace, fetches the full trace and walks every span.
4. ingests only spans with `status.code === 'error'`.
5. calls `upsertOccurrence` for each error span — creating the issue if it does not exist, or incrementing its count and potentially reopening it if it was resolved.

### cursors

the ingester tracks a **cursor** per service — the end timestamp of the last successfully processed window. cursors are persisted in an `ingest_state` table (one row per service).

- **first run (no cursor)**: window starts at `now − INGEST_INITIAL_LOOKBACK_MS` (default 1 h back).
- **subsequent runs**: window starts at `cursor − INGEST_OVERLAP_MS` (default 1 m back), to catch late-arriving spans that arrived after the previous window closed.
- the cursor never moves backward: it is always set to `max(previous cursor, computed end)`.

### adaptive window

when a Jaeger response returns exactly `INGEST_TRACE_LIMIT` traces (default 200), the ingester assumes the window may be truncated and halves the window scale for that service on the next tick. the floor is 5 s. when a tick returns fewer than the limit, the scale resets to 1 (full window).

this prevents high-traffic services from silently dropping traces during burst periods.

## Why issues survive Jaeger retention

the Jaeger in-memory backend caps at 10 000 traces and evicts old ones on restart. the ingester continuously copies error data — fingerprint, exception type, message, stacktrace, attributes, and the originating `traceId` + `spanId` — into the local database before eviction.

the `occurrences` table keeps `traceId` and `spanId`, so issue history and links to the originating trace persist even after Jaeger drops the trace. note: the link in the UI will 404 if the trace has been evicted from Jaeger.

## Honest limits

:::warning
these are real constraints, not roadmap items. understanding them helps you interpret the data correctly.
:::

**approximate latency and partial history**

the home error rate and per-service latency percentiles (p50 / p95 / p99) come from the engine's own stats ingester, not a dedicated metrics or SPM pipeline. percentiles come from a log-scale sketch and are accurate to about ±2 %. a service's stats start when the engine first sees it (the initial lookback is `STATS_INITIAL_LOOKBACK_MS`, 1 h by default), so longer ranges show "collecting since" until enough history exists. when a short interval still hits `STATS_TRACE_LIMIT`, its traces are counted as a sample and the dashboard prefixes counts with `≥`. Jaeger's SPM endpoint (`/api/metrics/…`) requires Prometheus or Elasticsearch storage that lightweight setups typically do not have.

**no upstream pagination**

Jaeger trace search returns a single result set per request, capped by `query.num_traces`. the ingester compensates with overlapping windows and adaptive shrinking, but during extreme bursts — many traces within a single short window — some may be missed. for high-cardinality services, consider a smaller `INGEST_POLL_INTERVAL_MS` or a persistent Jaeger storage backend.

**in-memory error filter caveat (Jaeger #8553)**

the Jaeger in-memory backend has a known bug where server-side error-tag filtering misses OTel error spans. the app never relies on server-side error filtering: it fetches full traces and detects errors client-side from `status.code === 'error'`. this is correct but means the ingester pulls all traces for a service, not a pre-filtered error subset.
